# 从读懂参考代码到亲手写 mkexe

本文由 AI 编写。`mkexe_reference.c` 是 AI 生成的学习参考;
`mkexe.c` 是留给你实现的入口。参考代码可以单独编译, 不参与正式工具的构建。
不必一次把它抄完: 每次只写一个能亲自观察结果的小步骤。

## 先确定工具的边界

mkexe 是运行在 Linux 上的宿主工具, 可以使用 stdio、malloc 和标准库。
`test.c` 是交给 LWOS 执行的裸机程序, 不使用宿主标准库。
两者使用不同的编译选项。mkexe 负责生成文件, resman 负责加载和运行。

整个方向是:

```text
你写的 test.c
    ↓ gcc 编译, ld 链接并保留重定位
  test.elf
    ↓ mkexe: 提取映像, 收集需要修正的位置, 写头
  test.lwp
    ↓ monitor 读取文件, resman 加载并重定位
  调用 lwp_main(env), 接收返回值
```

参考工具目前只实现读取文件和查看 LWP, 中间的 ELF 转换还没有实现。

## 头文件里的三个宿主对象

| 对象 | 保存什么 | 用在哪一步 |
|---|---|---|
| `MkexeOptions` | 输入/输出路径、ABI 需求、栈大小、标志 | 命令行给转换流程的配置 |
| `MkexeBuffer` | 文件字节指针和字节数 | 读 ELF 或 LWP |
| `MkexeImage` | LWP 头、映像字节、重定位数组 | 转换结果, 交给写出函数 |

这些对象不是磁盘文件的整体布局。尤其 `data`、`image` 等指针只在
宿主进程中有意义, 不能把整个对象写到文件里。
`LwpHdr` 才是文件头字段的描述; 写出时仍应逐个字段按小端编码。

## 参考代码第一段: get16 / get32

它们把文件中的小端字节拼成整数。例子:

```text
字节: 4c 57 50 00
整数: 0x0050574c = LWP_MAGIC
```

`get32` 的第 0 个字节占最低 8 位, 第 1 个字节左移 8 位, 以此类推。
先转换成 `uint32_t` 再左移, 保证高位字节参与无符号 32 位运算。
逐字节读取也不要求指针对齐。

可以先自己写一个只接受四个固定字节的程序, 用 `%08x` 打印结果。
之后再把输入换成文件的前四个字节。

## 第二段: range_ok

它回答: 从偏移 off 开始的 count 个元素, 每个 stride 字节, 是否都在文件里?

```text
文件 100 字节, off=80, count=5, stride=4: 正好到 100, 合法
文件 100 字节, off=80, count=6, stride=4: 到 104, 越界
```

参考写法先确认 `off <= size`, 再比较 `count <= (size-off)/stride`。
这样避免 `off + count*stride` 的整数溢出。`&&` 会短路, off 越界时
不会执行后半段的减法。这里 stride 只能是非零值, 现有调用传 1 或 4。

## 第三段: mkexe_read_file

操作顺序是:

1. `fopen(path, "rb")` 打开二进制文件。
2. `fseek` 到末尾, `ftell` 获取长度, 再回到开头。
3. `malloc` 分配缓冲区。
4. `fread` 将整个文件读到内存。
5. 关闭文件, 返回缓冲区和长度。

例如文件是 `4c 57 50 00`, 返回后 `out->size == 4`,
`out->data[0] == 0x4c`。读取失败要释放已经分配的内存。
空文件也分配 1 字节, 但 size 仍是 0, 不代表它多了一个文件字节。

不要一开始就写全部分支。先读取一个已知文件并打印长度,
再打印前几个字节, 最后补上打不开、短读和释放内存的处理。

## 第四段: mkexe_buffer_free / mkexe_image_free

释放这些对象拥有的内存, 然后把对象清零。
`main` 中 `{0}` 初始化保证错误路径也能释放它们: `free(NULL)` 是合法的。
接口约定是调用前对象为空; 不应把已有缓冲区的对象直接交给读取函数覆盖。

## 第五段: mkexe_dump

它只解释 LWP 文件, 不负责解析 ELF。分为三步:

1. 至少有 64 字节, magic、version、hdr_size 符合 v1。
2. 映像和重定位表在文件范围内, 入口在映像里, 内存长度不小于映像长度。
3. 打印字段, 遍历重定位表, 检查每个修正位置有完整的 4 字节。

`names` 从 flags 开始排列, 所以循环读取偏移 `8 + i*4`。
最前面的 magic/version/hdr_size 已经单独处理。

它还没有检查 CRC、表间重叠、重复重定位、未知标志等,
因此返回成功仅表示这些基础检查通过, 不能代替加载器的完整校验。

### 一个能手算的 LWP 布局

```text
文件偏移    长度     内容
0x00        0x40     LWP 头
0x40        0x20     映像
0x60        0x04     一项重定位: 0x00000004
文件总长: 0x64 字节
```

对应的头字段:

```text
entry=0, image_off=0x40, image_size=0x20
mem_size=0x30, reloc_off=0x60, reloc_count=1
```

映像需要 0x30 字节内存: 复制文件的 0x20 字节, 后面的 0x10 字节清零。
这些长度不包含独立栈。文件偏移与 RVA 是两种不同的坐标:

```text
映像内 RVA 0x04 → 文件偏移 0x40 + 0x04 = 0x44
映像加载基址 0x500000 → 内存地址 0x500004
```

若这个位置原来保存的是指针值 0x18, 重定位后应保存 0x500018。
重定位表里的 0x04 表示“去修改这里”, 不是“把指针指向这里”。

## 第六段: mkexe_from_elf / mkexe_write_file

这两个是占位函数, 当前打印未实现并返回 -1。
`(void)参数` 是避免编译器报告未使用参数, 不执行转换。

后续可以分开实现:

- 校验 ELF32、小端、i386、ET_EXEC, 确认按 0 地址链接。
- 查看 PT_LOAD 的文件偏移、虚拟地址、文件大小和内存大小。
- 创建全零映像, 把各段文件字节放到对应 RVA, 保留段间空洞。
- 检查未定义符号, 遍历重定位节。
- 收集 `R_386_32`; 内部 `R_386_PC32` 已由链接器处理, 不随基址变化。
- 注意 `SHN_ABS` 符号表示绝对常数, 不能无条件把它当成随基址移动的地址。
- 拒绝尚不支持的重定位类型, 再写出小端头、映像和重定位表。

先用 `readelf -h -l -r test.elf` 看真实输入, 不要同时写所有解析逻辑。
链接后的 `R_386_32` 对应字通常已经包含链接器算出的地址;
从 0 链接时, 加载器只需再加实际映像基址。

## 第七段: main

main 只安排流程:

```text
检查参数 → 读文件 → 查看或转换 → 成功才写出 → 释放内存 → 返回退出码
```

查看: `mkexe-reference -d example.lwp`
转换: `mkexe-reference test.elf test.lwp` (目前会报未实现)
退出码 0 是成功, 1 是处理失败, 2 是命令行用法错误。
默认 ABI 需求是 0, 后续应增加明确的配置输入。

## 建议的亲手实现顺序

1. 在 `mkexe.c` 接收一个文件名, 打印它。
2. 只读前 8 字节, 打印十六进制; ELF 应以 `7f 45 4c 46` 开头。
3. 读取整个文件, 打印大小, 正确释放资源。
4. 自己实现小端读取, 先做 LWP 文件头打印。
5. 用上述 0x64 字节的布局造一个样本, 检查你算出的偏移。
6. 对 `test.elf` 先打印 PT_LOAD 信息, 对照 readelf。
7. 最后逐步加入映像提取、重定位和写出。

每一步只增加一种行为。能解释每个变量指向哪里、每个偏移属于文件还是
映像、谁负责释放内存, 再进入下一步。参考代码的结构也可以按你的习惯调整。
